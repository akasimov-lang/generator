# Webdev: сетка, переклей и альтернейты

## Разовый массовый запуск: схема с фейк-внутряком (2026-09-23)

Список проектов пользователь предоставит отдельно. Требование относится к этому
списку, а не ко всем проектам базы. До получения списка запуск не выполнялся.
Для каждого проекта нужны три альтернейта:

```html
<link rel="alternate" hreflang="LANG-GEO" href="https://NEWREG/FAKE/" />
<link rel="alternate" hreflang="LANG" href="https://NEWREG/" />
<link rel="alternate" hreflang="x-default" href="https://DROP/" />
```

LANG и GEO берутся из проекта; NEWREG — новорег, DROP — дроп, FAKE — новый
созданный фейк-внутряк. Это обозначения для документации, не шаблоны Webdev.
История проекта и отчёт в чате должны содержать проект, прежний и новый Main,
а также фактический результат операции.

### Проверенный пример и canonical

Прочитаны клиентский код панели `index-CBEftfyt.js`, актуальный GET проекта
и публичный HTML главной и `/pelican/` на `pelicancasino-poland.com`.
В Webdev имя проекта — **pelican-casino-pl.com**, сервер — `horse`.
Домен `pelicancasino-poland.com` входит в его сетку; поиск проекта только по
этому имени в `/projects/cache` возвращает пустой список.

На момент проверки `settings.canon = 32m2treningu.pl`,
`settings.prev = pelicancasino-poland.com`. Фейковый путь `/pelican/`
присутствует в `settings.alternate.fakeMain`, выбран в `currentFakeMain`,
`enableDynamicRoutes = true`. Пользователь создал его вручную.

В `head` включены `enableCanonical` и `enableAlternates`:

```json
{
  "canonicalDefaultMarkup": "<link rel=\"canonical\" href=\"https://{{settings.canon}}{{reqPath}}\" />",
  "canonicalFakeMainMarkup": "<link rel=\"canonical\" href=\"https://{{settings.canon}}/pelican/\" />"
}
```

В интерфейсе это поля «Каноникл всех страниц» и «Каноникл главной и
фейквнутряков». При включённых альтернейтах второе поле применяется к главной
и **текущему** фейковому внутряку, а первое — к остальным страницам.
При выключенных альтернейтах, согласно пояснению панели, применяется первое поле.
Не следует предполагать, что второй шаблон распространяется на все старые внутряки.

Контракт сохранения из кода панели: `PATCH https://<server>/projects/update-head`,
JSON `{folder: projectName, enableCanonical: true, canonicalDefaultMarkup: "…",
canonicalFakeMainMarkup: "…"}`. Отправляются только необходимые поля.
В рамках исследования PATCH не выполнялся.

В публичном HTML обеих проверенных страниц canonical равен
`https://32m2treningu.pl/pelican/`, а альтернейты —
`pl-PL → https://pelicancasino-poland.com/pelican/`,
`pl → https://pelicancasino-poland.com/`,
`x-default → https://32m2treningu.pl/`.
Canonical следует за текущим Main через `{{settings.canon}}`; домен новорега
из альтернейтов не подставляется туда автоматически.

### Что учесть при исполнении

Локальная реализация обновлена: при автоматическом создании `activate_fake_main=true`
создание пути и выбор `currentFakeMain` отправляются одним `update-value`.
Остальные поля alternate сохраняются, включая редирект старых внутряков.
Ручное создание без этого флага сохраняет прежнее поведение.

Путь фиксируется в плане до записи и используется в языке-GEO и
`canonicalFakeMainMarkup`. Альтернейты и canonical сохраняются одним PATCH;
`enableCanonical=true`, существующий `canonicalDefaultMarkup` сохраняется,
при пустом поле задаётся стандартный шаблон с `{{reqPath}}`.
Завершение и очередь индексации ждут подтверждения Main, разметки, canonical
и действующего включённого фейкового пути чтением Webdev. Неопределённые ответы
не вызывают повторную запись; квитанции привязаны к UUID запуска.

Существующий порядок имён пока сохранён: GEO, GEO1…GEO10, GEO-язык,
бренд-GEO, бренд-язык, брендязык, бренд-casino-GEO, бренд-casino-язык.
Для общих ключей брендовые варианты исключены. Если бренд содержит casino
(без учёта регистра, в том числе слитное CatCasino), casino удаляется, берётся
первое оставшееся слово: Ice Casino → ice, King Billy Casino → king,
CatCasino → cat, Casino-X → x. Дополнительные варианты с casino для таких
брендов не генерируются. Если остаётся пустое имя (Casino), используются
только варианты GEO/языка. Добавлено продолжение GEO11, GEO12…
при исчерпании вариантов. Пропускаются обычные страницы, фейковые пути,
текущий путь и ранее наблюдавшиеся фейковые пути из `network_state.fake_main_history`.
История не восстанавливает пути, удалённые до первого наблюдения.
Уникальность проверяется внутри проекта, не между разными проектами.

язык-GEO, языкGEO; затем попросил показать существующие правила для проверки.
Новый порядок целиком пока не применён. Пользователь подтвердил, что повтор

сразу после бренд-язык в текущей очереди.

### Снимок для отчёта

После подтверждения в `AutoReglueRun.plan.applied_result` сохраняются имя проекта,
старый/новый Main, текущий фейковый путь, фактический `alternateMarkup`,
флаги включения, `canonicalFakeMainMarkup`, его версия с подставленным текущим
Main (`canonicalFakeMainResolved`) и время подтверждения. Следующий переклей
не переписывает предыдущий снимок. При неподтверждённой операции успешный снимок
не создаётся. Настройки Webdev и публичный HTML — разные уровни проверки:
перед окончательным отчётом массового запуска нужно также проверить теги на сайтах.

Колонки отчёта в чате: проект | старый Main | новый Main | новый фейк-внутряк |
применённая схема альтернейтов | canonical главной и фейк-внутряка (полный URL) |
результат. Для ошибочных/частичных запусков нельзя выдавать план за применённые
настройки; требуется чтение фактического состояния.

Изменения пока локальные, без запуска переклеев или выкладки.

Проверено 2026-09-16 по JavaScript панели Webdev 3.0
(`index-CBEftfyt.js`) и чтению проекта `betonredczech.com`.
Источник: https://webdev-alfasearch.ru/projects/betonredczech.com/

## Авторизация и чтение

- `POST https://o59s9a012jd.com/auth/login`: `{username, pass}` → `{token}`.
- Последующие запросы используют `Authorization: Bearer <token>`.
- `POST /projects/cache`: `{fields:{settings:true,head:true,data:false},names:[projectName]}`.
- Сервер проекта берётся из ответа: `serverIp`/`serverId`;
  короткое имя дополняется `.slf-hostesting.com`.
- `GET https://<server>/projects/one/<projectName>` возвращает объект
  проекта с `settings`, `head` и другими полями.
- Пароли и токены не сохраняются в документации и логах.

## Переклей: контракт из клиентского кода (запуск не выполнялся)

1. Выбрать резерв из `settings.domains`, исключив текущий `settings.canon`.
   Панель предлагает все домены сетки, а не только бывшие Main.
2. Сохранить выбор: `POST /projects/update-value`:
   `{folder: projectName, reserve: domain, reserveOption: domain}`.
   Клиент добавляет `reserveOption` при сериализации поля `reserve`.
3. Проверить доступность: `POST /projects/check-domain`, `{domain}`.
   Клиент читает `reachable` и `reason` из ответа. Недоступность выводится как
   предупреждение; пока проверка идёт, кнопка запуска заблокирована.
4. Запустить: `POST /projects/update-reglue`:
   `{trigger:"webdev:settings", folder:projectName, initiator:username, reserve:domain}`.
   Клиент допускает JSON-объект или строку с JSON, показывает `message` и проверяет
   `errors.length`, в том числе при успешном HTTP-статусе. Затем перечитывает проект.
5. Отдельная операция `POST /projects/update-domain`, `{folder:projectName}`,
   заменяет старый домен в доменных редиректах. Она не является запуском переклея.
6. Кнопка актуализации сетки: `POST /projects/settings-update`, `{ip:server, folder:projectName}`.

Ответы изменяющих запросов выше пока не проверены на живой записи: переклей,
резерв и редиректы в исследуемом проекте не менялись.

## Альтернейты: два разных набора настроек

### Разметка ссылок и x-default

Панель «Альтернейты» редактирует `head.enableAlternates` и `head.alternateMarkup`.
Переключатель сохраняется сразу, текст разметки — при потере фокуса.

`PATCH https://<server>/projects/update-head`

```json
{
  "folder": "betonredczech.com",
  "alternateMarkup": "<link rel=\"alternate\" hreflang=\"x-default\" href=\"https://www.mapovani.cz/\" />\n<link rel=\"alternate\" hreflang=\"cz\" href=\"https://bet-on-red-cz.com/\" />\n<link rel=\"alternate\" hreflang=\"cz-CZ\" href=\"https://bet-on-red-cz.com/\" />"
}
```

Это фактически выполненный запрос на `dolphin.slf-hostesting.com`: по прямой
просьбе пользователя исправлен только `.comm` → `.com` в ссылке `cz-CZ`.
Ответ — полный обновлённый объект `head`. Повторный GET подтвердил точное
совпадение разметки, неизменность остальных полей `head` и всего `settings`.
HTTP-код отдельно не записывался; curl подтвердил успешное выполнение запроса.

Включение: тот же PATCH с `{folder, enableAlternates:true}`.
Нужно отправлять только изменяемые поля, сохраняя остальные настройки.

### Копии главной и дополнительные настройки

`settings.alternate` сохраняется отдельно:
`POST /projects/update-value`, `{folder, alternate: <полный актуальный объект>}`.
Клиент объединяет изменённые поля с текущим объектом и отправляет с задержкой 1 с.

- `fakeMain`: список путей копий главной (например, `["/cz/"]`), не домены.
- `currentFakeMain`: выбранная копия (`"/cz/"`).
- `enableDynamicRoutes`: включение этих страниц.
- `redirectFakeMainsToCurrent`: отдельный переключатель редиректов копий.
- `alternateDomain`: домен из сетки для соответствующей схемы.
- `hrefLangs`, `alternateLang`, `alternateReserveDomain`,
  `useMainDomainInAlternateScheme`: сохраняются при редактировании объекта.

Не выводить историю Main из `fakeMain`. Не смешивать `settings.alternate`
с HTML-разметкой `head.alternateMarkup`. Историю x-default можно фиксировать
по хосту ссылки `rel="alternate" hreflang="x-default"` в разметке.

## Создание поддомена — проверено на реальной задаче

2026-09-16 через форму «Создание/удаление доменов» добавлен
`test1.bet-on-red-cz.com` в проект `betonredczech.com`.
После ввода и Enter домен попадает в preview; запись выполняется только кнопкой
«Создать конфиги». Поддомен определяется по родительскому домену сетки;
для него `wwwPrimary=false`.

Фактически отправленный запрос:

```http
POST https://o59s9a012jd.com/site-config/create
Authorization: Bearer <token>
Content-Type: application/json
```

```json
{
  "server": "dolphin.slf-hostesting.com",
  "project": "betonredczech.com",
  "username": "anton",
  "port": "1141",
  "domains": [
    {
      "id": "1789547850608-0.6239334109349224",
      "domain": "test1.bet-on-red-cz.com",
      "wwwPrimary": false
    }
  ]
}
```

Ответ HTTP 201: `{"jobId":"1504","skipped":[]}`.
`id` — идентификатор строки в форме, генерируется заново для новой строки;
`port` берётся из актуальных settings проекта, нельзя фиксировать его глобально.
`skipped` содержит домены, уже существующие в сетке, и требует отдельной обработки.

Статус задачи приходит через SSE:
`GET https://o59s9a012jd.com/site-config/1504/stream?token=<token>`.
Токен в URL потока нельзя записывать в журналы.

Наблюдавшиеся этапы: авторизация → базовый конфиг → сертификат → обновление
конфига → актуализация сетки → задача создания поддомена CDN/DMS → задача
мониторинга DMS → перезагрузка Nginx.
Дополнительный запрос добавления в сетку из браузера не отправлялся: это этап
серверной задачи создания.

Терминальное событие: `state="completed"`, `progress=100`,
`result.successCount=1`, `result.errorCount=0`, `error=null`.
Внутренний `domains[].status` в этом событии остался `pending`: нельзя принимать
его за единственный признак завершения. Панель при `completed` отображает
успех для доменов без статуса `error`.

Проверено отдельным GET проекта: домен присутствует в settings.domains,
в сетке 17 доменов, canon/reserve/alternateMarkup сохранились.
`HEAD https://test1.bet-on-red-cz.com/` вернул HTTP 200 с корректным HTTPS.

## Реализация в панели генератора

- Две вкладки: «Сетка» и «Переклей». Поле для пользователя называется «Альтернейты».
- `GET /api/sites/{site_id}/network` читает актуальное состояние Webdev и сохраняет
  наблюдавшиеся Main (включая известный prev), домены альтернейтов и x-default.
- `POST /api/sites/{site_id}/network/check-domain` проверяет выбранный резерв.
- `POST /api/sites/{site_id}/network/operations`: `action` = `reserve`, `reglue`
  или `alternates`, UUID `request_id` и `revision` актуального снимка.
- Резерв сохраняется отдельно; перед переклеем сервер повторно проверяет его
  принадлежность сетке, отличие от Main, сохранение и доступность.
- Альтернейты сохраняются PATCH update-head. `settings.alternate`, включая
  fakeMain/currentFakeMain, этой операцией не меняется. Для будущих шаблонов
  остаётся то же поле разметки; шаблоны пока не добавлены.
- Конкурентные изменения обнаруживаются по revision. PostgreSQL advisory lock
  исключает одновременные операции через нашу панель. Внешний API не предоставляет
  условную запись, поэтому полностью исключить изменение в другой панели между
  проверкой и записью нельзя.
- Квитанция операции записывается до отправки. Таймаут не вызывает повторную
  отправку. Статусы pending/unknown блокируют новые записи до подтверждения
  ожидаемых значений чтением проекта. Отдельная задача отложенного обновления
  не требуется: открытая вкладка перечитывает состояние каждые 10 секунд.
- Успешный HTTP-код не равен подтверждению: учитываются errors/success/error
  в ответе и фактические настройки после записи. Журнал не содержит токенов.
- Миграции 0042/0043 добавляют историю и журнал операций; старые поля не удаляются.


## Проверки при навигации

Открытие проекта читает сохранённый результат меню из нашей БД через
`GET /sites/{id}/menu-capabilities`. Этот GET не запускает Chromium, проверку
шаблона или синхронизацию проекта. Старые сохранённые boolean-результаты
отдаются даже без checked_at; дата не выдумывается.

Сетка и переклей используют один экземпляр панели: при переключении между
ними дополнительных запросов нет. Первое открытие читает актуальную сетку
из Webdev; ручное обновление и подтверждение незавершённой операции продолжают
читать актуальное состояние. Проверка резервного домена запускается своей кнопкой.

Проверки меню запускаются явно кнопками. Завершённая проверка сохраняет результат
и время в sites; ошибка повторной проверки не удаляет предыдущий результат.
Проверка шаблона не заменяет сохранённый результат видимости вложенного меню.
Обновление данных проекта выполняется отдельной кнопкой «Обновить проект».

Регрессия запросов: `frontend/tests/workspace_requests_browser.py`,
переменные CHROME и VITE_TEST_URL как в остальных browser-сценариях.

### Создание поддоменов из вкладки «Сетка»

Форма между таблицей и альтернейтами принимает до 100 полных имён через
пробел, запятую или новую строку, показывает список перед запуском.
POST network/operations с action=create_subdomains и domains=[...] использует
тот же журнал UUID-операций, блокировку и защиту от повторной отправки.

До авторизации в Webdev сервер проверяет Site.cache_domains (скачанный кэш):
родитель обязан присутствовать в сетке, новый адрес не должен уже существовать.
www у родителя считается вариантом корневого домена. Протоколы, пути, wildcard,
некорректные DNS-имена запрещены. После локальной проверки перечитывается Webdev,
проверяется revision и принадлежность актуальной сетке.

POST /site-config/create идёт на центральный project_cache_url, с текущим
сервером проекта, port из settings и учётной записью Webdev из серверной
конфигурации. Номер задачи и skipped показываются в журнале. Статус подтверждается
появлением всех адресов в сетке; это не подтверждение готовности сертификата
или завершения всех этапов CDN/DMS. При неизвестном ответе повторная запись
блокируется, чтение сетки продолжается. Реальных поддоменов в ходе тестирования
этой формы не создавали.

### Тип домена

Столбец «Тип домена» сохраняет ручной выбор drop («Дроп») или newreg
(«Новорег») в Site.domain_types, отдельно от скачиваемого кэша.
Без выбора показывается «Не указан»; тип не угадывается.
PATCH /api/sites/{site_id}/network/domain-type принимает domain и domain_type,
проверяет наличие домена в сохранённой сетке/истории и обновляет только его запись
под блокировкой строки. Webdev не вызывается. GET network возвращает domain_types.
Значения сохраняются при смене Main и обновлении сетки. Это метаданные проекта
для дальнейшего использования автоматизацией; текущие настройки дропа для
x-default и родителя новорега автоматически не переписываются.

## Удаление домена из сетки
Контракт подтверждён по Webdev panel JS (processDelete, useDeleteSiteConfigTaskMutation):
POST центрального /site-config/delete, JSON {server, project, username, domains:["test1.example.com"]}.
В отличие от create, domains — строки, port не передаётся. Ответ содержит jobId;
текущее состояние задачи доступно через /site-config/{jobId}/stream (SSE).

Наша action=delete_domain принимает один domain, request_id и revision. Проверяет
принадлежность локальной и актуальной сетке. Нельзя удалить имя проекта/net, Main,
резерв и домен из действующих альтернейтов. UUID-квитанция фиксируется до отправки;
таймаут не приводит к автоматической повторной записи. Удаление подтверждается
отсутствием домена в актуальной сетке; история Main/альтернейтов/типов сохраняется.

### Защита переноса и цели после переклея

Перед выбором донора и непосредственно перед извлечением проверяется актуальный
`settings.redirects` исходного проекта. Участие домена с любой стороны редиректа
запрещает его перенос; варианты с `www` относятся к тому же защищённому домену.
Move +1/+2 и перекрёстный переклей пропускают такие кандидаты. Если редирект
появился уже после плана, сервер блокирует удаление до создания квитанции и
очереди. Частичный ответ без списка редиректов не подтверждает их отсутствие.
Удаление редиректа снимает это ограничение при следующем актуальном чтении;
это не постоянная отметка БАН.

При смене Main сохраняется намерение обновить конечные цели, ведущие на прежний
Main. Промежуточные звенья и независимые пользовательские назначения сохраняются.
Редирект с самого нового Main убирается, чтобы новый Main отдавал страницу;
например, `a → b → old` становится `a → b → new`. Если Webdev уже обновил список,
дополнительной записи нет. Иначе создаётся отдельная квитанция `reglue_redirects`
и штатным `update-value` сохраняется актуальный список с новыми целями.

Подтверждение переклея и индексация ожидают подтверждения редиректов. При таймауте
запись не повторяется, результат проверяется чтением; продолжение после смены
Main восстанавливается по сохранённому намерению без повторного переклея.
Старые операции без такого намерения автоматически не изменяются. До/после
хранятся в истории операций. Общая реализация используется ручным, внутренним
авто- и перекрёстным переклеем.

### Компактное обновление сеток в списке проектов

Кнопка с круговой стрелкой рядом с настройками столбцов перечитывает сетки всей
текущей отфильтрованной выборки, независимо от страницы и отметок чекбоксами.
Для каждого проекта вызывается `GET /sites/{id}/network?refresh=true`, затем

### Выбранный резерв и массовый переклей

- В перекрёстном массовом запуске выбранный резерв своей сетки имеет приоритет: становится Main без извлечения и добавления доменов. Домен, совпадающий с текущим Main, считается уже использованным резервом.
- При отсутствии резерва план использует только свободный новорег другого проекта того же бренда и GEO. Дропы не подменяют новореги в этом режиме; правило одного дропа сохраняется отдельно для Move.
- Сетка с резервом не получает импорт через Move или перенос с переклеем. Её другие свободные домены могут быть донорами. Оба поля Webdev `reserveOption` и `reserve` защищены от извлечения, в том числе с `www`.
- План и выполнение проверяют резерв повторно перед извлечением; групповое извлечение проверяет всех получателей. Уже отправленные операции не повторяются. Смешанные группы ждут извлечений до смены Main; локальный переклей не создаёт очередь переноса.
- В таблице доменов выбранный резерв получает статус «Резерв»; имя домена и статус выделены жирным, как Main. Резерв и Main находятся в конце списка (сначала резерв, затем Main), в том числе при показе истории. Отдельной колонки «Резерв» в списке проектов нет. Сохранённые настройки удалённой колонки и её сортировки очищаются при открытии списка.

### Альтернейты в истории проекта

Боковая история сетки показывает подтверждённые операции `alternates` вместе со
сменами Main и внутряка, в общем порядке по времени (последние 20 событий).
Состояния до/после берутся из квитанции `NetworkOperation`, а не из текущего кеша;
старые квитанции тоже видны. Если исходный снимок отсутствует, интерфейс явно
показывает отсутствие данных. Разметка выводится как текст, без исполнения HTML.

Для новых подтверждений сохраняется неизменяемый `confirmed_at`, для старых
используется ранее записанное `updated_at`. Отображение времени — МСК. Ожидающие
и ошибочные операции остаются в подробном журнале операций и не считаются
подтверждёнными обновлениями. Сохранение без изменения альтернейтов (в том числе
правка только canonical) не добавляет событие в боковую историю. История Main,
дата последнего переклея и недельные ограничения переклеев при этом не меняются.


В истории сетки и отчётах сравнение альтернейтов показывает разметку «Было / Стало» (или «Запрошено / Планируется»), без подписей «Включены / Выключены». Это постоянное предпочтение пользователя: переданная разметка подразумевает включённые альтернейты. Исходные флаги в снимках сохраняются для проверки операций; это правило оформления отчётов, не изменение настройки публикации или проверки результата.
