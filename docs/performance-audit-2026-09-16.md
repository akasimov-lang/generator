## Подтверждённые источники лишней работы

1. frontend/src/main.tsx: loadAll запрашивает auth, sites, providers,
   tasks, archive, content и для администратора dashboard/users.
   Фоновая загрузка убрана из критического пути первого отображения, но
   сами глобальные ответы всё ещё запрашиваются.
2. refreshProject вызывает onChanged (= loadAll), затем loadProject.
   В активных разделах polling вызывает onChanged каждые 1.5 или 4 секунды.
   Локальное обновление способно повторно загрузить данные всей системы.
   Зависшие статусы могут поддерживать такой polling.
3. Общий /content возвращает ContentItemResponse с полным содержимым.
   Для списков проекта уже используется облегчённая проекция.
4. /sites отдаёт полную модель каждого проекта; среди крупных полей
   cache_domains, menu_library, default_menu. ORM дополнительно читает
   network_state, хотя оно не входит в SiteResponse.
5. API запускается одним процессом Uvicorn. Некоторые async-обработчики
   выполняют синхронные обращения к БД; publish-immediately на ветке
   publication_failed вызывает синхронный fetch_project_cache.
   Это потенциальная блокировка цикла API, а не доказанная причина
   конкретного наблюдавшегося зависания.
6. Основной Celery worker concurrency=4 обслуживает общую очередь:
   генерацию, публикации, индексацию, автопереклеи и периодические задачи.
   menu_checks и project_stream уже вынесены отдельно.
7. GET /sites пересчитывает сохранённые уведомления по локальной БД.
   Это два пакетных чтения, не внешний Webdev, но лучше обновлять состояние
   при событиях публикации/проверки/изменения меню и сверять фоном.
8. У publication_logs нет индекса site_id + created_at.
   Накопительные seq_scan не доказывают медленный запрос:
   индекс требуется подтвердить планом выполнения.
9. Gzip, длительное кеширование версионированных JS/CSS, кеш вкладок 30 сек
   и объединение совпадающих GET уже работают. Повторное внедрение не требуется.

## Предлагаемый порядок

### 1. Убрать глобальные перезагрузки из локальных действий

Уточнённое требование пользователя: общий список проектов запрашивается
только при активной странице «Сайты» и явном нажатии «Обновить проекты».
Открытие страницы само по себе не запускает обновление.

- Показывать последний сохранённый компактный снимок списка и время обновления.
  Клиентское хранилище изолировать по пользователю; при отсутствии снимка
  показывать понятное приглашение обновить список.
- Рабочий экран и прямой URL проекта загружают только выбранный проект через
  отдельный endpoint по ID/имени; не зависят от получения всех 1298 проектов.
- Выбор проекта использует сохранённый справочник; при необходимости отдельный
  адресный поиск, а не загрузку полного кеша.
- Не обновлять общий список по таймеру, после публикации, при прогрессе
  генерации или переключении вкладок. Локальные изменения отражать адресно.
- Поток обновлений внешнего кеша может обновлять серверную БД по проекту,
  не заставляя браузер перечитывать общий список.

- Обновлять только данные текущего проекта и затронутые счётчики.
- Архив, административные страницы и общий контент читать при открытии.
- Возвращать краткие списки; текст статьи получать при просмотре/редактировании.
- Добавить компактный справочник проектов, детали брать отдельно.
  Сохранить поиск по доменам всей сетки через отдельный поисковый индекс/эндпоинт.
- Не запускать новый polling, пока предыдущий не закончен.
- При неактивной вкладке браузера приостанавливать частый polling;
  при возвращении проверять состояние, фоновые задачи продолжаются.

Ожидание: многократное уменьшение передаваемых данных и числа лишних запросов
в цикле обновления. Коэффициент ускорения всего интерфейса пока не измерен.

### 2. Изолировать фоновые операции от API и друг от друга

Схема: браузер → короткий API-запрос → сохранённая задача → очередь → worker.
Браузер получает ID и наблюдает прогресс; закрытие браузера не отменяет работу.

Отдельные очереди: длительная генерация; публикация/подтверждение/индексация;
автопереклеи; проверки меню; короткие служебные задачи планировщика.
Начать с перераспределения текущего бюджета параллелизма, затем настроить
по нагрузке. Не увеличивать все workers без измерений.

- Ограничить CPU, память и соединения БД фоновых workers, оставить запас API/БД.
- Проверить два API-процесса; перед этим вынести миграции/инициализацию
  из параллельного старта. Beat и потребитель stream должны оставаться
  единственными либо иметь лидерство/блокировки.
- Долгие внешние операции вынести из HTTP; сохранить сообщения, этапы и ошибки UI.
- Короткие транзакции; не держать блокировки БД во время ожидания внешнего сервиса.
- Heartbeat/lease, контроль зависания, ограниченные повторы и устойчивый ID операции.
- Перед повтором мутаций сверять результат с проектом, не допускать двойного
  переклея, публикации или индексации.
- Outbox/сверка БД с очередью: сохранённая задача не должна теряться между
  commit и отправкой Celery.

На одном сервере полной физической независимости нет: общими остаются
диск, БД, Redis и ядро ОС. Если нужна независимость от сбоя/перегрузки хоста,
следующий шаг — отдельный сервер фоновых workers.

### 3. Обновлять UI по событиям

SSE из нашей системы сообщает ID проекта и что изменилось; клиент загружает
только изменённый блок. При разрыве связи — возобновление и резервный редкий
опрос. Событие отправлять после commit. Уже существующий project_stream —
входящий поток внешнего кеша, он не заменяет канал событий для браузера.

### 4. Точечная оптимизация БД, журналов и сборки

- Проверить EXPLAIN, затем добавить нужные составные индексы, начиная с журналов.
- Пагинация журналов; полные request/response payload читать только при раскрытии.
  Историю не удалять ради ускорения.
- Состояние уведомлений обновлять событийно с фоновой сверкой;
  GET не должен становиться основным механизмом исправления состояния.
- Делить фронтенд по страницам (сейчас единый JS около 681 KB до сжатия).
- Ограничить срок/объём кеша сборок и настроить уборку только build cache,
  не томов PostgreSQL/Redis. Освобождение диска само по себе не обещает
  ускорения вкладок; это запас для стабильной работы.

## Как доказать эффект и сохранить поведение

Перед изменениями собрать p50/p95 API по маршрутам, размер ответов,
время первого отображения и переключения, длительность ожидания в очереди,
занятость workers и задержки БД. pg_stat_statements сейчас не установлен.
Не писать токены и содержимое статей в метрики.

Сравнить одинаковые сценарии до/после: тёплая/холодная загрузка;
генерация + публикация + проверка меню одновременно; 1/5/10 пользователей
на стенде с копией данных и подменёнными внешними мутациями.

Цели для проверки, не обещания: сократить фоновый трафик не менее чем в 5 раз,
убрать повторную загрузку всех проектов при работе с одним,
обеспечить целевой p95 лёгких API <300 мс на сервере под выбранной нагрузкой.
Точные цели браузерного времени зафиксировать после базового замера.

Регрессии: ручной и автоматический переклей, приоритет персональных настроек,
расписание и защита повторов, AMP-исключения, подтверждение кешем,
альтернейты, индексация, сохранение уведомлений и прав доступа.
Изменения вводить этапами с возможностью отката.
