# Предпочтения интерфейса PagePilot

- Все новые и перерабатываемые выпадающие списки делайте с поиском: пользователь может ввести название или код и выбрать вариант из списка.
- При открытии показывайте полный список, даже если значение уже выбрано. Фильтруйте только после ввода пользователя.
- Поддерживайте выбор мышью и клавиатурой, Enter, Escape, закрытие по потере фокуса и сообщение об отсутствии результатов. Отмена поиска сохраняет выбранное значение.
- В полях ГЕО показывайте флаг страны рядом с кодом и названием, в стиле существующих полей PagePilot.
- Эти требования — постоянное предпочтение пользователя для следующих доработок проекта. Обычный select или браузерный datalist не являются заменой поискового списка.

# Проверки изменений

- Не запускать локальный Google Chrome, Chromium или Playwright на Mac пользователя. Для изменения этого правила нужно новое явное указание пользователя.
- Выбирать проверки по файлам текущей задачи и затронутым зависимостям. Не запускать тесты всех незакоммиченных изменений: рабочее дерево содержит изменения других задач.
- Использовать `python scripts/check_changes.py <изменённые файлы>` для просмотра списка проверок; `--run` запускает только выбранные проверки без браузера.
- Для неизвестного узла явно указать связанные тесты через `--test`, а не считать отсутствие выбранных тестов успешной проверкой.
- После успешной проверки не повторять её без новых изменений, обнаруженной ошибки или нерешённого риска. Полный прогон нужен при изменении общих моделей/БД/инфраструктуры тестов или при обоснованной сквозной регрессии.

## Выкладка production

- Изменения кода и конфигурации production доставлять только Git-коммитами и `git push production main`, после синхронизации с `origin`.
- Не применять scp/rsync/docker cp или прямую правку исходников на сервере как способ выкладки.
- Перед выкладкой проверять расхождения рабочего дерева production с Git. Не затирать их: сначала сохранить и согласовать в репозитории.
- Секреты, сертификаты, БД и резервные копии в Git не добавлять. Hooks деплоя хранить в `scripts/git-hooks/`.
- Успех выкладки подтверждать health checks и совпадением SHA `main` с `generator.git/deployed-revision`.

## Управление витринами

- Перед исследованием или изменением витрины читать `docs/integrations/showcase-management.md` и следовать алгоритму определения реального источника.
- Сохранять внутренние системные пометки о подключении и способе управления; не считать отсутствие casinos отсутствием витрины: проверить code/raw/table, используемые шорткоды, layout и баннеры.
- При добавлении брендов существующие карточки и бонусы не менять без явного поручения. Не смешивать части разных бонусных предложений.
- Каждая новая или перерабатываемая витрина должна иметь новый стильный дизайн; перед работой читать `docs/integrations/showcase-design-protocol.md`. Не тиражировать одинаковую оболочку карточек и не скрывать условия. Концепцию и отличия сохранять в отчёте.

## Изображения статей

- При публикации текста сначала загружать все его изображения в папку соответствующего проекта Webdev. В опубликованном содержимом использовать относительные ссылки на файлы проекта; не оставлять ссылки на media API PagePilot.
- Подтверждать наличие и загрузку файлов до успешного статуса публикации. Ошибка загрузки изображения блокирует публикацию статьи; повтор не должен бесконтрольно дублировать файлы.

## Таблицы и кнопки в обзорах казино

- Каждый обзор казино должен содержать информативную таблицу: казино и оператор, лицензия, год основания или запуска с пояснением, приложение и платформы, примерное количество игр и провайдеров, наличие бездепозитного бонуса, платёжные системы, контакты поддержки и способы связи. Приблизительные значения обозначать; не выдумывать факты для заполнения.
- Добавлять кнопку перехода с именем обозреваемого бренда + «вход» в переводе на язык проекта. Проверять оформление и добавлять стили, если их нет.
- По общему правилу кнопку можно размещать в разных местах обзора, только между целыми блоками: не разрывать абзацы, таблицы и списки. Повторная публикация сохраняет выбранное место.
- Для проекта junckerassociates.com / stanleyvillage.info кнопку размещать непосредственно перед информационной таблицей; чешская подпись — «Бренд — přihlášení».
- Контекстная ссылка на главную не заменяет ссылку в хлебных крошках: обе сохранять при генерации и публикации.

## Технические страницы без автоматических витрин и изображений

- На технические и служебные страницы (cookies, контакты, условия, о проекте, конфиденциальность и аналогичные) никогда автоматически не добавлять витрину, карточки казино, баннеры или изображения статьи — при генерации, публикации и массовых вставках. Общие логотип, шапку и футер сайта сохранять. Исключения возможны только по отдельному явному поручению пользователя.
- Кнопки перехода к казино подключать к существующему трекингу проекта; сохранять подтверждённые split-параметры. Не придумывать новые split-маршруты. Внешним ссылкам на бренды задавать rel=nofollow. Навигационные кнопки и внутренние ссылки не перенаправлять в трекер.

## Webdev-задачи для редиректов фейковой страницы

- После каждого подтверждённого переклея и смены фейкового внутряка проверять полный выбранный URL на новом Main, даже если путь внутряка не менялся, сохраняя завершающий слеш. При HTTP 301 создавать Webdev-задачу в связанном проекте Fibery со статусом New, конкретным URL проекта и страницы, фактическим и требуемым направлением редиректа. Выбранная страница должна отдавать 200 напрямую; если проблема только в слеше, вариант URL перенаправляется 301 на выбранный адрес, без петли.
- Не создавать дубликаты открытых задач для одного проекта и URL; сохранять ссылку в PagePilot, подтверждать описание и привязку чтением из Fibery. Смена пути отменяет устаревшую проверку. Сетевую ошибку не считать подтверждением редиректа.
